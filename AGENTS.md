# Repository Guidelines

## Project Overview

Live map of Berlin S-Bahn, U-Bahn, and tram vehicles. A static SPA (no backend): the browser polls VBB's HAFAS endpoint (`fahrinfo.vbb.de/gate`) directly every 20 s, renders vehicles as line-colored badges that animate smoothly along track shapes. Buses, regional, and express trains are excluded by a server-side product mask plus a client-side line-name gate. English UI; German station/direction names as delivered by the API.

## Architecture & Data Flow

```
poll() — every 10s, paused while the tab is hidden (backoff ×2 up to 60s)
  —▶ fetchAllVehicles(BERLIN_BBOX): one request per PRODUCT_GROUPS mask, in parallel, merged by jid
  POST https://fahrinfo.vbb.de/gate?rnd=<Date.now()>   (HAFAS JourneyGeoPos, rect in microdegrees, PROD mask 7)
  └▶ parseRadar → transformJourney (cls gate + strict line-name gate) → Vehicle[]
render(): filterVehicles(filters) → reconcile markers → updateSegment (AnimState anchored at
  current animated position, arrival = Date.now() + timeDiffMs(schedule))
rAF loop (dt clamped ≤100ms): advanceAnimation (forward-only, accel-limited velocity toward
  operator forecast, replayed along the track) → marker.setLngLat
  (keeps moving until fresh data); debug target paths rebuilt ≤ every 500ms
Track shapes: public/routes.json → lineShapes[line] (GeoJSON [lon,lat] → [lat,lon]);
  buildSegmentPath slices the shape between projected from/to (direction-aware), straight-line fallback
```

Import graph: `main.ts → {hci.ts, vehicle.ts, motion.ts, track.ts, line-colors.ts, style.css, maplibre-gl}`; `hci.ts → vehicle.ts`; `track.ts → motion.ts`; `vehicle.ts`, `motion.ts`, `line-colors.ts` are pure leaves.

## Key Directories

- `src/` — all app code; tests colocated (`src/<module>.test.ts`)
- `public/` — static assets served as-is: `stations.json`, `routes.json` (animation geometry) + `tracks.json` (drawing geometry), all GTFS-derived and generated, `maplibre-gl-worker.mjs` + `maplibre-gl-shared.mjs` (vendored MapLibre build artifacts — Vite does not emit the worker)
- `scripts/` — `prepare-data.mjs`: one-off GTFS + linienfarben → static assets + `src/line-colors.ts`
- `docs/plans/` — design doc and implementation plan (historical; the plan's Leaflet stack was superseded by MapLibre GL)

## Development Commands

```sh
npm install              # npm only (package-lock.json)
npm run dev              # Vite dev server → http://localhost:5173 (binds IPv6; use `localhost`, not 127.0.0.1)
npm run build            # tsc --noEmit && vite build  (TS check + production build to dist/)
npm test                 # vitest run (single pass, no watch)
npm run preview          # serve the built dist/
npm run prepare:data     # regenerate stations.json/routes.json/line-colors.ts from GTFS (rarely needed)
```

Debug view: tick **Debug view** in the panel, or append `?debug=1`. (`?all=1` is gone — every mode the gate returns is shown by default now, so there is nothing left for it to unlock.)

## Code Conventions & Common Patterns

- **Language/style**: TypeScript strict (`strict: true`), ES2022 target, no path aliases. ESM with `.js` extension in relative imports (`import {x} from './motion.js'`). No eslint/prettier config in the repo — match existing formatting. No framework; vanilla TS + MapLibre GL.
- **Naming**: `PascalCase` types/interfaces (no `I` prefix), `camelCase` functions/variables, `UPPER_SNAKE` constants. Types carry docs that state invariants (read them — e.g. `AnimState`, `Vehicle.stops`, `Vehicle.toStop`).
- **Error handling**: data transforms return `null`/undefined for missing data (never throw); `parseRadar` throws on HAFAS `err != 'OK'`; network failures drive the poll backoff state machine (`live | stale | offline`); static-layer fetches use `try/catch` + `console.warn`. Never add try/catch around animation math.
- **Async**: no async/await in the hot path. Polling is a recursive `setTimeout` chain with a fresh `AbortController` (15 s timeout) per poll; animation is a single rAF chain with `dt = Math.min(now - lastFrame, 100)`.
- **State management**: module-level mutable `Map`s (`animStates`, `markers`) + a `vehicles` array; map view persisted to `localStorage['liveberlin.mapview']` (validated on load, saved on `moveend`). No DI, no stores.
- **`stopL` is NOT a stop chain (measured, 308/308 journeys)**: `JourneyGeoPos` always returns exactly 4 stopovers — `[origin, previous stop, next stop, destination]`. Only [1] and [2] are adjacent; [0]/[3] can be an hour and half a city away. Never infer the current segment geometrically from this list. Take it from `jny.ani.fLocX[0]` / `ani.tLocX[0]` (indexes into `common.locL`), surfaced as `Vehicle.fromStop` / `Vehicle.toStop`. `ani` also carries the 30 s motion forecast that drives the animation: `mSec` offsets plus `polyG.polyXL` -> `common.polyL[].crdEncYX` (Google encoded polyline, lat before lon). Its point count always equals `mSec`'s (4, 10 s apart) and point[0] is exactly `jny.pos`.
- **Poll interval is 10 s**, matching the official VBB livemap (`_.Livemap.timeout = 10` in their `hafas_webapp_config.js`). `trainPosMode` has only two values (`CALC`, `CALC_REPORT`); `REPORT` alone is rejected and `CALC_REPORT` returns identical positions, so there is no GPS-based mode. The community wrappers (`v6.vbb.transport.rest`, `v6.bvg.transport.rest`) are dead, and gtfs.de's GTFS-RT is CORS-blocked with no VehiclePositions — this endpoint is the best browser-direct source available.
- **`routes.json` holds SEVERAL variants per line name, not one** (533 features, 48 lines). A line has branches and short turns, and the two ring directions (S41/S42) run different track, so one shape per line name left 6.3% of live vehicles (23 of 367) projecting 300 m-6.5 km off. `pickShape` chooses per vehicle by forecast fit — the forecast is the only evidence of which branch a vehicle is on, because HAFAS names the next stop but not the route to it, and a headsign is not a route (live U7: six destinations, two termini; M5 reaches one depot by two streets). Measured: `badFit` 7.9% -> 0.14-0.4% of segment rebuilds, residual p50 10 -> 4 m, p90 86 -> 19 m.
- **Build-time shapes are simplified with Douglas-Peucker at 10 m** (`scripts/simplify.mjs`), never decimated to a point count. Nth-point decimation kept every Nth point regardless of geometry — wasting points on straight runs and cutting corners on curves — which is what put residuals in the ~100 m band `SHAPE_FIT_LIMIT_M` was sized around. DP bounds the error by construction: GTFS's 708k points become 117k, and shipping 11x more shapes made the payload *smaller* (76 -> 54 KB gzipped).
- **Overlapping "redundant" variants are NOT redundant — do not prune them.** 365 of 533 variants run entirely along a longer one, and it is tempting to drop them: they make `pickShape`'s choice ambiguous (median residual gap to the runner-up 0.0 m, 42% of vehicles change variant within 60 s). Pruning was implemented and measured, and it was clearly WORSE: reversals 5.9 -> 31.4 per 100 s, `badFit` 0.14% -> 0.91%, drift p90 26 -> 52 m, max 1086 -> 1838 m, overspeed 0 -> 7 (same hour, same code). A short variant gives a vehicle a SHORT, unambiguous shape to project onto; forcing it onto the full-line variant makes `projectOntoPath` ambiguous, which is the same mechanism that sank the length tie-break. The earlier claim in this file that "a short turn projects onto the longer one correctly" was wrong.
- **`maxResidualM` is degree-space BY DESIGN, and making it accurate makes things worse.** It goes through `projectOntoPath`, which finds its nearest point treating 1 deg lon as 1 deg lat (at Berlin longitude is 0.61 of that), overstating residuals by a mean 1.8 m and up to 7.5 m depending on the track's bearing. Replacing it with true perpendicular metres was implemented and measured WORSE on every axis: drift p90 26 -> 50 m, reversals 5.9 -> 13.6 per 100 s, overspeed 0 -> 3, `badFit` 0.14% -> 0.38%. The reason is CONSISTENCY, not accuracy: `buildSegmentPath` slices with `projectOntoPath` and `alongsOnPath`/`total` pace from the same projection, so selecting with a different metric picks the shape that fits best by one measure and paces it by another. `projectOntoPath`, `pointAlongPath`, `slicePath` and `maxResidualM` must all move together or not at all.
- **Data-prep gates need FLOORS, not just ceilings.** Collapsing every shape to its two endpoints — the symptom of a units or tolerance bug — passed every earlier gate at 4.7 KB against a real 54 KB, and would have shipped straight chords for the whole network. Gates now check mean points per shape, a minimum gzipped size, a variant-count range, and that every coordinate is finite and inside Berlin. Verified by deliberate sabotage. Writes stay inside the `else` branch, so a failure never overwrites committed assets.
- **A forward-only hold must be time-boxed** (`MAX_HOLD_MS`, 2 s) and must yield SLOWLY (`REVERSE_MAX_SPEED` 3 m/s floor, `REVERSE_TAU_SEC` 10 s). `forwardStep` refuses to move a badge against its heading, and `main.ts` only refreshes the heading when the badge moves >= 0.3 m — so a held badge could never move again, and the only escape was the target coming round to the front (on a ring line, a whole lap). Measured before the fix: 33.5% of vehicle-samples still while the forecast said they were moving, 8 of 8 vehicles caught mid-freeze were correcting, gaps up to 5,697 m, and drift max ~2 km in every recording. Raising the hold to 6 s made it WORSE (reversals 25 -> 53 per 100 s): the duration is not the lever, the yield rate is. After: freezes 13.8 -> 0 per 100 s, reversals 3.4 per 100 s at 0.4 m each, drift p90 61 -> 28 m, max 2088 -> 443 m. Do not remove the yield to suppress a reversal.
- **`maxResidualM` measures true metres, not degree space.** `projectOntoPath` finds its nearest point treating 1 deg lon as 1 deg lat (at Berlin, longitude is 0.61 of that), so the foot point it returns is not the true nearest: residuals were overstated by a mean 1.8 m, up to 7.5 m, varying with the track's BEARING. Harmless against a 250 m threshold, fatal for `pickShape`, which discriminates on a few metres. `projectOntoPath`/`pointAlongPath`/`slicePath` still share degree-space units — they are self-consistent with each other, and changing them is a separate job.
- **`SHAPE_FIT_LIMIT_M` (250 m) is still needed as a backstop**, now firing on 0.25% of rebuilds instead of 7.9%. When nothing fits, `updateSegment` follows the forecast points extended straight to the target. The 250 m figure is measured: residuals are bimodal, with shape-vs-track noise up to ~100 m and branch mismatches from ~300 m. A tighter limit left ~46 vehicles on the boundary, flipping path source between polls and jolting the marker.
- **Measure animation changes with an A/B in the SAME hour, and never with other JS running in the page.** Freeze and drift counts move a lot between hours (a baseline read 4 per 100 s one evening and 8.6 the next), so cross-hour comparisons are worthless. And an in-page measurement loop that scans every vehicle against every variant starves the rAF loop and manufactures the very freezes it reports — one contaminated run showed 28 freezes/100 s and drift p90 174 m, against 11.8 and 106 m for the same build measured cleanly.
- **Animation invariants (do not break)**: motion is a replay of the operator's own forecast (`Vehicle.forecast`: positions at `ani.mSec` offsets), projected onto the GTFS track and evaluated against wall clock — nothing is schedule-paced or invented. Progress never decreases (`alongAt` clamps and forces `alongs` non-decreasing). Past the forecast, coast at the last sample's speed rather than freeze. Anchor each poll on the **reported** position, not the previously drawn one: measured drift is ~9 m median, so being truthful costs no visible jump (max step 12 px over 74k samples). Never re-introduce schedule pacing — it measured 356 m median error, *worse* than not animating at all (197 m).
- **Motion is forward-only across polls too** (`AnimState.drawnAlong`): each poll re-anchors on the reported position, which can sit *behind* what we extrapolated, and snapping back reads as the vehicle reversing. `advanceAlong` holds until the forecast catches up. Measured: 305 reversals / 80 s over 183 vehicles before, 13 after. Do not "simplify" this to a plain `alongAt` call.
- **Coasting expires** (`COAST_GRACE_MS`, 5 s past the last forecast sample). Before this, a 45 s outage left 251 of 276 markers still gliding on a stale prediction. Coast far enough to cover a late poll, not far enough to invent a journey.
- **The rendered position is forward-only too** (`forwardStep`, `AnimState.heading`). `stepTowards` has no sense of direction, so easing toward a position that sits *behind* the badge dragged it backwards; `drawnAlong` only guarantees monotonic progress along ONE path, and a poll re-projects onto a new one. Measured: 40 reversals per 100 s before, **0** after.
- **A track the forecast could only follow at an absurd speed is the wrong track** (`impliedSpeed`, `SPEED_SANITY_MPS` = 45 m/s). The 250 m fit check passes shapes that take a much longer way round, and ring lines (S41/S42) where projection wraps to the far side. Two vehicles were sustaining 320 and 214 km/h; after the guard, none above 160 km/h.
- **Corrections are rate-limited in POSITION space** (`stepTowards`, `AnimState.renderPos`). `advanceAlong` only smooths progress along one path; each poll can replace the path entirely, and a point projected onto a *new* path can land far from where the badge was drawn — that was a 988 m single-frame jump, seen as the badge blinking out and reappearing ahead. `CATCHUP_MAX_SPEED` (400 m/s) plus the hard `CATCHUP_MAX_STEP` (25 m/frame, for stalled frames) bound it. Measured over 580k frames: max 14 m/frame, none over 25 m, zero reversals. Normal motion is far under the cap, so it lands exactly on target with no lag.
- **VBB PUBLISHES NO MEASURED POSITIONS. Every dot is computed.** Do not go looking for a way to make positions "more accurate" — there is no position data to be accurate about. Proved three ways on 2026-08-27:
  - `trainPosMode` accepts `CALC`, `CALC_ONLY`, `CALC_REPORT` and `REPORT_ONLY` (the enum rejects `REPORT`/`NONE`, and the error message lists the rest). **`REPORT_ONLY` returns ZERO journeys for every one of the seven modes** — S-Bahn, U-Bahn, tram, bus, ferry, ICE/IC, RE/RB. `CALC_REPORT` returns exactly what `CALC` does, so nothing is reported and nothing falls back.
  - The official VBB GTFS-RT feed (`production.gtfsrt.vbb.de/data`, no auth, CORS on, CC BY 4.0, 60 req/min) carries **7,232 TripUpdates and 0 VehiclePositions**.
  - HAFAS barely revises its own view: its +30 s forecast against the position it later calculates for that instant is median 7 m / p90 24 m over 1,966 tram pairs. A model fed by telemetry would keep correcting itself.
- **The position is an interpolation between two MINUTE-ROUNDED anchors.** Every arrival and departure string in the feed is a whole minute — 1,762 of 1,762 checked, scheduled and realtime alike — and tram stops are 1-3 minutes apart (median 2). So a tram between stops is drawn from two numbers: leave at minute X, arrive at minute Y. The rounding alone is ±30 s, which at 7-8 m/s is ±200-250 m, before the real vehicle's own accelerating and waiting at lights. The delay feed itself is live and working (56% of realtime arrivals differ from schedule). Practical consequence: the map is right at stops and least reliable mid-segment. `popupHtml` says so on every vehicle; do not remove that line to tidy the popup.
- **Our own contribution to the error is small, and the track choice is not the problem.** Measured for M10 and 12 (the lines a user reported as looking wrong), 259 s, 22 vehicles, 15,569 frames: drift against the reported position median 3 m / p90 56 m, zero freezes, 5 reversals of 0.3-0.5 m, no overspeed. Residual of the forecast to the chosen GTFS variant, in true metres over 145 live trams: median 2.8 m, p90 6.0 m, max 10 m, nothing over 25 m. We are on the right street; the uncertainty is how far along it. Polling faster cannot help — the model does not change between polls.
- **Known remaining inaccuracy in OUR code: `projectOntoPath`, `pointAlongPath` and `slicePath` measure in degree space.** They use `hypot(dlat, dlon)`, so at Berlin (1 deg lon = 0.61 deg lat in metres) east-west distance is over-weighted by 1.64x. The three are self-consistent, so nothing breaks, but along-track distance is not proportional to true distance: pacing between two forecast samples is uneven wherever the track turns. Bounded by one 10 s sample interval (~50-80 m of travel) and self-correcting at the next sample, so worst case is roughly 20 m at a corner. Fixing it means one cosine factor applied consistently in all three, and it MUST be A/B measured in the same hour — two other "obvious" improvements in this area both measured worse (see the `maxResidualM` and `pickShape` notes above).
- **Accuracy must be measured mid-poll-cycle.** Sampling right after a poll flatters the animation (frozen positions are perfect then) and understates error. At a controlled 6 s after each poll: drawn median 7-14 m / p90 61-72 m, frozen median 58-68 m / p90 110-129 m, drawn closer for ~82% of vehicles.
- **The filter UI is two MULTI-selects: Type, then Line.** Each is a `<details>` holding a checkbox list, not a `<select multiple>` — that needs ctrl/cmd-click for a second choice and is close to unusable on touch. The summary carries the current choice (`all`, `none`, `S-Bahn, Tram`, `M4, M10, S1`, or `4 lines` past three), so the panel stays one line per filter until opened.
- **An EMPTY line set means NONE, not all** (`filterVehicles`). It used to mean "all", which broke the master checkbox: "All lines" could only tick itself, the individual lines stayed blank, and unticking it did nothing. Now both master boxes behave the same way — tick to select every item, untick to select none, and an empty selection empties the map exactly as unticking every type does.
- **`lineMode` (`'all' | 'custom'`) is what makes that safe.** In `'all'` the app passes `undefined` for the line filter, so every line shows and a line that starts running later joins on its own — which also keeps things correct before the first poll has answered and no line is known yet. The first tick of an individual line calls `makeSelectionExplicit`, seeding `lineFilter` from what is currently ticked; ticking every line again returns to `'all'`.
- **The two filters stay coherent by two rules:** the line list only offers lines of ticked types, and `dropHiddenLines` forgets a picked line whose type is switched off — otherwise the map empties with no visible reason. Lines sort with `compareLineNames`: numeric part numerically, so U9 precedes U12, and bare tram numbers precede the M lines.
- **Both menus list only what is RUNNING** (`liveLines`, keyed by `lineKey`, fed by `recordLineSightings` from every poll). They used to be seeded from `tracks.json`, the whole network: ~190 lines, of which a Sunday morning runs about 90 and a weeknight far fewer, so most entries selected nothing and you could not tell which. `presentTypes()` derives the Type list the same way, so a night with only trams out shows one type. Two consequences to keep: a line lingers `LINE_LINGER_MS` (60 s, six polls) after its last sighting, so one poll that misses a line's only vehicle does not move rows under the pointer; and the menus rebuild ONLY when the set of names changes, for the same reason. A picked line that stops running stays in `lineFilter`, so it comes back ticked — but `describeLines` counts only what the menu offers, or the caption would name vehicles that are not on the map. Before the first poll, both menus show a `.multi-hint` line rather than an empty box.
- **EVERY mode is fetched and shown** (`ALL_PRODUCTS = 1023`). Measured by asking the gate for one product bit at a time (2026-08-27, 20:39): cls 1 `S` 16 lines / 137 vehicles, cls 2 `U` 9 / 107, cls 4 `Tram` 27 / 186, cls 8 `Bus` 187 / 673 (sub-label `Kleinbus`), cls 16 `Fähre` 1 / 1, cls 32 `ICE`+`IC` 3 / 3, cls 64 `RE`+`RB` 17 / 27. Bits 7-9 are accepted and return nothing. Every one of the seven carries the same `ani` forecast — position, stop list and the 30 s polyline at `[0,10000,20000,30000]` — so nothing about the animation is rail-specific.
- **One request CANNOT hold every mode: the gate caps a response at 1,000 journeys** (`JNY_CAP`). `maxJny` 2000 and then 5000 both returned exactly 1000, against 1,134 counted one bit at a time, and which ~130 it drops is not ours to choose. So `fetchAllVehicles` sends one request per `PRODUCT_GROUPS` mask (`7`, `8`, and the rest) in parallel and merges by `jid`: bus alone is ~675 and everything else ~460, both clear of the cap. Measured per poll: 814 KB + 1,341 KB + 79 KB = 2.2 MB, 0.3-1.5 s each. Keep bus in a group of its own — it is 60% of both the vehicles and the bytes. If a group ever does hit the cap, `capped` puts `feed capped` in the status bar and a line in the log; do not let that failure be silent.
- **Polling stops while the tab is hidden.** At 2.2 MB a poll a forgotten background tab would pull ~13 MB a minute for nobody. The rAF loop already stops by itself in a hidden tab. Coming back polls at once. `schedule()` REPLACES the pending timer and `inFlight` guards re-entry — an earlier version added a timer instead and would have run two poll loops side by side.
- **`cls` decides the mode and nothing else does**, and the `LINE_PATTERNS` name gate is rail-only for a reason. A rail replacement bus is named after the line it replaces: the live feed carries a BUS called `S9`, a BUS called `U6` and a BUS called `M1`. A name pattern applied to bus would reject real services, and worse, trusting the name over `cls` would file those buses under S-Bahn, U-Bahn and tram. The three rail patterns stay only because FEX is known to arrive under a rail cls bit. An unmapped `cls` is dropped, never guessed.
- **Lines are identified by MODE AND NAME** (`lineKey`, `product:line`). Keyed on the name alone the bus `S9` and the S-Bahn `S9` collapse into one menu row, and ticking it shows both. `lineFilter`, `liveLines` and `filterVehicles` all work in these keys; only the label shown to the user is the bare name.
- **The four non-rail modes ship no GTFS geometry, and animate on the forecast instead** (`guardStats.noShape`, ~1,900 of 3,240 rebuilds). `updateSegment` skips `buildSegmentPath` when a line has no shape and uses the forecast points continued straight to the target — which is what the `badFit` fallback already did. This is deliberate, not an omission: the forecast IS road geometry for the next 30 s, buses stop every ~400 m so the straight tail is short, and shipping bus + regional shapes was estimated at 2-4 MB gzipped against 56 KB for `routes.json` today. Berlin has 187 bus lines and VBB GTFS covers all of Brandenburg, so that work also needs a bbox filter before it is worth doing.
- **The Line menu has a search field** because with every mode on about 265 lines run at once and 187 are buses. It sits OUTSIDE `.multi-list`, which `rebuildLines` replaces on every tick — rebuilding an input takes the focus and the caret with it. "All lines" still covers every selectable line, not just the ones matching the query: a master box that quietly meant "the 3 matching rows" would be a trap.
- **Every published line colour is shipped, not just rail** (`scripts/colors.mjs`, 82 entries). The CSV has per-line colours for RE, RB, FEX and the X buses, plus mode fallbacks named `Tram`, `Bus` and `Fähre`; only the single-letter DB category rows (P, R, S, T) are dropped, as they are categories rather than lines. A replacement bus named `U6` therefore draws in U6's colour — deliberate, and useful to a rider. Product fallbacks live in `PRODUCT_COLORS` in main.ts: bus `#a5027d` and ferry `#009bd5` are VBB's own, ICE/IC and regional are greys the CSV has no row for.
- **Product gating**: `cls` bit → product for all seven modes; the `LINE_PATTERNS` second gate (`/^S\d{1,2}$/`, `/^U\d{1,2}$/`, `/^M?\d{1,2}$/`) applies to the three RAIL products only, because FEX can arrive under a rail cls bit. Never extend it to the others — see the note above on replacement buses.
- **Timing**: always pass `Date.now()` (not rAF `performance.now()`) to `advanceAnimation` — different time bases.
- **MapLibre gotchas**: `setWorkerUrl('/maplibre-gl-worker.mjs')` must run before `new Map(...)`; `addSource`/`addLayer` only after the map `load` event. Layer order matters and the adds race: `addTargetsLayers` runs on map `load`, `loadNetworkLayers` after a fetch, so the network layers pass `belowDebug()` as `beforeId` to stay under the overlay. Final order is `routes-layer`, `stations-layer`, `anim-paths-casing`, `anim-paths-layer`, `targets-layer`; vehicle markers are DOM elements and always sit on top.
- **One `Debug view` switch owns the whole test overlay** (`body.debug`, persisted in `localStorage['liveberlin.debug']`), and the switch itself only EXISTS in a dev build or under `?debug=1` (`DEBUG_AVAILABLE`). The site is published: a visitor must not meet test controls, and `?debug=1` is the hatch that still lets the built site be diagnosed. The remembered setting is only honoured — and only written — when the switch is on screen, or someone who ticked it once would be stuck with the overlay and nothing to clear it with. It controls the vehicle ID captions (`body.show-vids`), the target/path layers (`targets-layer` + `anim-paths-layer` + `anim-paths-casing`), the `#debuglog` panel and the motion recorder, all inside `#debug-group`. Off by default. This replaced four separate switches plus two layers whose code sat commented out behind `// TESTING:` markers — which is how the app ended up shipping a test view with no way to leave it. Do not comment out a layer to hide it; put it behind the switch.
- **`routes.json` is for ANIMATING, `tracks.json` is for DRAWING. Do not mix them.** `routes.json` holds one entry per route variant, because `pickShape` needs a short, unambiguous shape to project each vehicle onto. Drawing it is wrong: drawing every variant is 11,451 km of line over ~1,029 km of actual track — 11x. `tracks.json` is 22 features, one MultiLineString each, 12 KB gzipped.
- **Merge by RENDERED COLOUR, not by line.** Merging per line still left up to ten strokes on one tram street (measured: `18+21+27+37+62+67+M17+M4+M5+M8` share rails in 32 places), and all 22 tram lines render in the same red — linienfarben has no per-tram-line colour, only a generic `Tram` row — so those ten strokes were one set of rails drawn ten times. The feature's `group` property is a hex when the line has its own official colour, or a product name when it falls back, so no product hex is duplicated in `prepare-data.mjs`; the UI resolves a non-hex key through its own `PRODUCT_COLORS`. Same-colour families (S2/S25/S26, S46/S47, S7/S75, S8/S85) merge correctly because they really are one colour. Result: the tram network draws 187 km against Berlin's real ~190 km.
- **Merging tracks works on CELLS, and coverage must not be edge-sensitive.** Matching variants segment by segment fails, because each was simplified on its own so two paths over the same rails have different vertices. So resample every variant to 8 m and mark the cells it covers. Each covered point marks its own cell AND the eight around it: plain cell equality was boundary-sensitive, because two GTFS shapes for one street differ laterally by several metres, so a point near an edge landed in the next cell, read as uncovered, and the track was drawn twice. That left 40.6% of tram segments with a duplicate within 12 m; the 3x3 mark took it to 3.0% (the rest are junctions). `CELL_M` 12 with the 3x3 block gives a 6-18 m merge distance. Two other constants were tuned on real data: `GAP_TOLERANCE` 8 samples (at 3, output came out as thousands of 2-3 point fragments — 42,160 points and 662 KB gzipped, against 3,600 and 12 KB) and `MIN_RUN_M` 80. Coordinates are rounded to 5 decimals: resampling produces 17-digit floats that cost 39 bytes each and barely gzip.

- **Line layers still fade in with zoom.** `routes-layer` is `minzoom: 11` with width 0.8-2.6 and opacity 0.3-0.7 across z11-16 — below z11 the whole tram network falls inside a few hundred pixels and vehicles are the subject. `anim-paths-layer`/`anim-paths-casing` draw one path per VEHICLE, so they stack as deep as the traffic: ~270 vehicles merged into a solid orange band, and both are `minzoom: LABEL_MIN_ZOOM` (13). Target dots and station dots stay: discrete points do not smear. Station dots are `minzoom: 12` because 1,573 of them out-number the vehicles.

## Testing & QA

- **Framework**: Vitest 2, node environment, no globals (`describe/it/expect` imported explicitly), no mocks/spies/fake timers, no coverage thresholds configured. Run with `npm test` (or `npx vitest run`).
- **Style**: one `describe` per function, one `it` per behavior; inline literal fixtures (HAFAS JSON, path arrays) with `as never` casts; assertions `toBe`/`toEqual`/`toMatchObject`/`toBeCloseTo`/`toThrow`.
- **Layout must fit any realistic window**: `#map` is 100% of the viewport; every overlay is capped with `max-width`/`max-height` against the viewport and scrolls internally. Below `COMPACT_MAX_WIDTH` (720 px — the filter panel needs ~270 px and the status bar ~220 px, so narrower windows would overlap) `body.compact` hides the panel behind `#settings-toggle`. Verified across 14 real device/window sizes and a 29-step resize sweep. Note MapLibre resizes its canvas one frame *after* the container, so measure layout after two `requestAnimationFrame`s, never synchronously.
- **Motion is checked by recording, not by watching.** The debug view has a **Record motion** toggle and **Save log** button (`src/recorder.ts`); analyse the download with `node scripts/analyse-motion.mjs logs/motion-*.ndjson [--vehicle 75416-24]`. Fault detection (`jump`, `reversal`, `overspeed`, `freeze`, `dwell`, `correction`, `appear`, `vanish`) runs on **every animation frame**, because a teleport lasts exactly one frame; the position trace is sampled at 5 Hz (`?traceHz=N`) because storing every frame for every vehicle is ~350 MB per 15 min. Drive it headlessly via `__lb.startRecording()` / `__lb.stopRecording()` / `__lb.saveRecording()`.
- **Never judge speed on a single frame.** `stepTowards` may move 25 m in one frame (1560 m/s) while correcting, and a move that lands just inside the frame budget is not even flagged as correcting. Per-frame speed reported **17198 false overspeeds in 15 min**. Overspeed is therefore measured over `MOTION_LIMITS.speedWindowSec` (10 s), which separates a sub-second re-anchor from real speed; a 3 s window did not. Per-frame faults are caught by `jumpM` instead. After the fix: 24 overspeeds in 100 s, all genuine.
- **Coverage**: 151 tests (motion 46, vehicle 29, track 25, recorder 19, `scripts/simplify` 11, hci 5, polyline 4). Note `scripts/simplify.test.mjs` lives outside `src/` — build-step helpers are pure and worth testing, so the co-location convention extends to `scripts/<module>.test.mjs`. Note two test files live in `scripts/`, not `src/` — the build-step helpers (`simplify.mjs`, `variants.mjs`) are pure and worth testing, so the co-location convention above extends to `scripts/<module>.test.mjs`. `logs/` is gitignored; a 15 min recording is ~98 MB. Pure modules (`motion`, `track`, `vehicle`, `hci` parsing) are well tested; **`main.ts` is entirely untested** (map init, markers, render/frame loop, filters, polling/backoff, view persistence) — it would need a DOM environment plus a maplibre-gl mock; `fetchVehicles` network behavior and `line-colors.ts` are also untested.
- **Verification workflow**: `npm run build` (type-checks via `tsc --noEmit`) then `npm test`; UI changes are verified in a real browser against `localhost:5173` (the dev server running), since main.ts has no tests. For headless checks use the `window.__lb` handle (`{map, animStates, vehicles, lineShapes, logs, byId(jidOrShortId)}`, exposed at the end of `main.ts`); `logs` mirrors the on-screen `#debuglog` panel, which stays hidden until something is logged or read DOM state (`.veh[data-vehicle-id]`, `document.querySelectorAll`) — console event capture is unreliable.
